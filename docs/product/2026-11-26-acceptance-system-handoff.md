# 下一轮 handoff：让验收成为交付能力

2026-11-26（上海）｜设计基线 `608aef32`；本轮只更新方案，不执行发布、迁移、生产写入或清理。功能清单 **12/29 已关闭，17 项未关闭；D08 独立结算**。以下编号是待执行的交付单，不是新增功能父项或已创建的 PR。

**交付目标：** QA 拿到一个候选和一个执行入口，就能创建隔离数据与真实测试身份，用 Ego Browser 重跑验收并出具可核对的报告。第一阶段只打通批审核心链：**创建夹具 → 正常登录 → 真实落库后丢响应 → 按原编号查询和重放 → 对账 → 清理 → 校验报告**。首链成功后再扩模块，不先造通用测试平台。

## 为什么卡住，改什么

- **缺少可重建的业务初始条件。** 正式站没有安全的 121 条审核数据、第二审核员和可丢弃的资源。正式站不是数据工厂。改为由验收工具创建真实测试身份和业务状态，按运行编号归属、可计数、可清场。
- **缺少可控制、可观测的边界。** 过去回执协议替换、Cookie 切换后刷新、CDP 延迟，是不同的证据，不能拼成一次真实的失联恢复、会话切换或性能测试。改为在隔离环境控制请求什么时候到达和响应什么时候交付；Worker、数据库、会话和 UI 仍按真实产品逻辑运行。
- **缺少贯穿发布的版本身份。** [R3 证据](../operations/evidence/2026-11-24-cr-batch-local.md)记录了 `dec03894` / `index-CPb6Xb9H.js` 和 R3-F03 的四类受控响应（每项 1 GET，0 个审核 POST），以及此前 AC-01 首发真实丢响应。前者证明部署前端的分类行为，后者不是仅 B 子集；两者都不能补部署 ID 或替代同候选的完整报告。既有全量 unit/worker 结果保留为代码证据。
- **VM 有独立的产品准入条件。** 握手、安装、终端、持久状态和正式入口是不同能力。测试 VM 要成为可重建的配套交付物，而不是借一个环境完成演示。

**选型：** 不在正式单库靠测试标题、特权账号或开关隔离；采用**同候选代码与前端资产、不同资源绑定**的验收 Worker。纯本地 Worker/D1 适合先开发和回归，但不顶替目标环境中的 Ego 旅程。沿用 Ego Browser：正式域名做候选版本核对及批准的无业务写入冒烟；隔离域名做真会话、写入、故障、并发和容量。**这改变了旧的“产品验收仅正式站”规则，需产品/发布签署用哪类证据关闭哪一项**。未签署可以准备隔离工程证据，不能据此关闭父项；若仍要求所有场景必须在正式域名跑，另立正式测试租户设计并评审鉴权、数据、DO、外发、限流与故障隔离，不能直接用生产现状凑数。

### R4-02 · 把身份、样本和清场做成一个入口（后端 + QA；依赖 R4-01）

- [ ] 新增拟定 `tools/acceptance/` 的 `prepare / verify / clean` 三个子命令和版本化夹具。`prepare` 建管理员、委托审核员、Contributor 和用来验证无审核权限的账号/状态，复用现有密码登录、角色服务和 Worker schema；登录在 Ego 正常进行，测试凭据仅通过受控渠道领取。优先经产品接口建数据；若量大，用**仅隔离目标**的一次性种子加正常 API 回读，不新增生产造数端点。
- [ ] MVP 夹具包括两条恢复投稿和独立分页组。分页组为 **121 条**，排序固定（含唯一并列键），先记录目标总数和按页 ID，走产品 UI 验 50 行第 2 页、100 行第 2 页（各至少有 21 条），同页选到 20、第 21 拒选、翻页清空。写入后核对每条回执，第 21 条和夹具外对照项不变；重跑可能改状态的路径前重建组，不靠共享队列凑页数。容量增大只在隔离环境，不引入面向生产用户的批导入功能。
- [ ] 生命周期 `prepare → verify → run → clean → verify-clean`。首版每个隔离目标同一时段最多一个写入租约，冲突时可见失败。只按运行清单的精确归属释放数据、测试凭据/会话以及关联资源；失败保留回单，重试幂等；过期未清理显式报警，不能接着复用污染环境。验收：同一版本连续准备/清理两次结果相同；中断后能重试清理；改目标、混入非运行记录或找不到归属时拒绝并保留对照项。证据必须能区分残留业务夹具和保留的报告/审计。

### R4-03 · 拿到真实失联、子集晚到和精确回执证据（QA 工程 + 审核后端；依赖 R4-02）

- [ ] 在 `tools/acceptance/` 建**独立于产品路由**的测试传输控制，使用 `src/routes/admin-review.ts` 的真实端点和真实 D1。控制面只供隔离执行器，限定目标、方法和该轮精确编号，有时限且一次性；未命中正常透传，无任意代理或生产开关。不改生产资产/Worker 源来接受故障标志；不编辑浏览器存储来制造 unknown。
- [ ] 在 Ego 走两条路径：首发和仅 B 子集。子集场景先造出可观察的「A 已成功、B 暂不写入且可重试」；优先复用现有真实业务失败路径；若没有确定路径，先单独交付隔离测试适配器，证明 **B 尚无业务写入**，不能伪造 B 的持久成功。重试 B 只把 B 发送给真实 Worker，控制器扣住下游响应；另一路权威读证同一编号已落库后才丢弃客户端响应。日志顺序必须是「Worker 调用及 D1 回读成功 → 客户端未获响应 → 自然 unknown」。只有 200 或刻意不消费响应体不算通过。
- [ ] 同一浏览器保留旧 A/B 读取，进入仅 B 的新轮再释放旧响应；记录旧轮已取消或迟到结果被拒收，只有 B 回执出现，「仅重查」没有 A GET，旧错误/loading/复制反馈不改当前轮次；回到同一成员下刷新再恢复，按**原编号和原请求内容**重放。权威结果和审计前后对照：A、B 各一次业务结果、各一条决策审计，非样本不变。单独核对 401/403 终止，以及权威 404/通用 404/5xx/错身份 200 的分类，不能把替换响应当作 Worker 协议证据。交付 R3-F02/F03、R3-E01 和 WP01/WP13 的可复跑记录，不单独关闭 D02。

### R4-04 · 支持真实会话变化，验证旧页面不会继续显示旧数据（前端 + 身份后端；依赖 R4-03）

- [ ] 先用隔离 Ego 验两个真实审核账号、普通成员、无权角色的路由/API 矩阵。两独立任务空间只证明授权对照，不当作同页切换。实测同一任务空间从另一标签正常退出 A、登录 B 时，原审核标签收到什么信号。当前 [`frontend/app.tsx`](../../frontend/app.tsx) 在挂载时读一次会话；路由 key 只能处理已被上层发现的变更，不负责发现 Cookie 背后的会话变化。
- [ ] **拟交付产品行为：** 同源其他标签退出、登录变化或受保护请求获权威授权失败时，旧页面失效；窗口重新可见时支持有界会话复核。以真实 `/api/session` 为权威，标签间信号只触发复核，不传身份或权限、不授予访问。复核若确认主体/权限变化，旧 owner 取消只读请求并清屏；过期写入结果不得导航或回填，不声称已取消服务端提交。若产品评审选择明确退出并重新登录的边界，仍需实际验证旧标签失效，组件测试覆盖同实例重新渲染；不人为加隐藏的热切换按钮或把两标签 Cookie 注入计为通过。先写复核频率/失败 UI 的接受标准，不引入无界轮询。
- [ ] 用已登录 A 在原审核页发队列/回执读取并延迟回包；同一浏览器经正常流程换 B，再在原标签观察复核和 B 自己的菜单/队列；放行 A 的旧回包。另跑撤权与重新授权，以及旧写入晚到不导航。通过：旧行、编号、复制提示、旧轮次新发 GET 和旧导航均为 **0**，B 不恢复 A 的意图，A 回来仍能按原号恢复且无自动审核 POST。由 QA 核对 `/api/session`、菜单、路由和 Worker 各自结果。覆盖 R3-F01、R3-V01a、V02a；角色编辑参见 R4-06a。

### R4-05 · 复跑性能预算，超标才立优化单（前端性能 + QA；依赖 R4-03）

### R4-07 · 交付可重建 VM 和支持矩阵（VM Owner + QA；依赖 R4-01）

- [ ] 用 Ego 启动该轮真实 VM，分别验终端（实际退出码/输出）、重载和生命周期恢复、文件持久性（摘要一致）、允许网络目的地及拒绝/撤权、退出后清理（运行对象、租约、临时文件均有回单），随后重建一轮得同样结果。固定可用的联网验收目标只证明所测能力；LC-010 GitHub 超时仍按原决定跳过、未验。G0 未满足则仍走诊断/隔离入口，不将探针挂到正式菜单。若测试环境或某承诺能力在支持矩阵内不可交付，由产品决定投入修复或正式调整范围；保留历史缺口，不把 D04 改写成通过。

### R4-08 · 把同候选验收接进发布关项（发布 + QA；依赖相应场景证据）

- [ ] 在现有发布流水线产出 `Candidate/Run/CaseResult` 报告和校验器，先用 R4-03 跑一次端到端。报告把 `rtk npm run check`、场景产物与候选锁在一起；新构建、绑定或 schema 变化时明确失效范围，重跑受影响场景。同候选配置通过后，走现有正式发布流程，在 Ego 核对正式版本与获准的无业务写入冒烟。WP04 的 0081 精确 `d1_migrations` 台账行及目标绑定由发布方提供；不授权额外查询或迁移。
- [ ] 关项校验拒绝 SHA/部署/场景错配、缺失资源回读或清场回单、以及 `blocked/not-run` 充作通过。报告须可在 Ego 打开，区分隔离验收与正式站观察。只有父项在登记的必需场景都合格才更改[原功能清单](./2026-09-12-personal-workbench-completion-audit.md)，随后跑 `rtk npm run audit:functional-checklist`。R3-V00/V06 → D07；D08 按发布/迁移规则独立，不由测试平台关项。不因单次正向成功跳过授权、恢复或清理对照。

### R4-09 · 单独结清生产遗留记录（数据负责人；不阻塞 R4-01–08）

- [ ] 将证据记录中的 **4 条**已驳回投稿逐条与精确 ID、来源、关联审计对账，登记「授权保留」或「待授权删除」。未明确授权则不写 D1，正式站不自动造数，不按标题或日期范围删除，不为验收临时增加生产删除 API。
- [ ] 若决定保留，给负责人、理由和复核时间；若授权删除，由具备权限的 D1 操作者先只读确认精确 ID 与依赖，再按批准的最小范围处置，提供受影响行数和处置后核对。两种结果都要有回单，不和隔离数据清理混为一谈。

## 接手时先做什么

1. 产品和发布先完成 **R4-00** 的证据口径及资源责任，QA 用两份旧证据演示拒绝错误关项。在资源未开通前，可用本地 Worker/D1 开发 R4-01/02 的契约与拒绝错误目标，不去生产收集新的写入样本。
2. 第一份可交付里程碑是 **R4-03 同一个 `runId`** 的全链回单：正常登录、A/B 实际恢复、精确编号和持久化对账、清理后无残留，并能核对候选版本。没有达到就记录是环境、产品代码、夹具还是取证故障；不把后续所有工作重新列为“请用户提供”。
3. 扩面后，新功能设计必须同时给出：可重建前置数据、真实身份路径、可观察的业务结果、失败/恢复场景、清理责任和候选映射。缺这些可以开发探索，不能提交关项请求。全量通过前保留失败和未验状态，不改计数。
