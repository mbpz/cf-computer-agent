## 候选机制：集中准入与可证明排空

建议后续评审一个集中协调器，状态为 `OPEN → DRAINING → FROZEN → RESUMING → OPEN`。可候选使用 Durable Object 的串行准入和持久化状态；新增 binding、可用性、免费产品限制、调用开销及失效方案必须在实施前验证，本稿不承诺平台容量。所有具备 D1 写可能性的入口必须接入同一协调器，不能靠各实例本地布尔值或最终一致配置实现互斥。

1. **OPEN：** 每个工作先申请唯一工作许可并绑定维护 epoch。协调器先登记再允许执行；失败时关闭准入。许可覆盖整个工作及其子任务、waitUntil、取消处理和最终写入，不能在 Response 返回时提前释放。后续异步工作要么继承未释放许可，要么单独申请，不允许脱离跟踪。
2. **DRAINING：** 单一控制动作持久化关闭新准入；尚未获得许可的 HTTP 返回 503、scheduled 不启动。已有许可继续完成。不得仅等待固定秒数便视为清零。
3. **FROZEN：** 只有所有已登记工作完成、异步写者停止、外部写路径受控，且所有活跃部署均已接入准入时才能进入。记录 epoch、部署集合、零活动工作证据、操作者和窗口 ID，不记录内容。丢失/悬挂许可不可依赖 TTL 自动抹除；未知状态继续阻塞，人工核对或按已验证取消方案处理。
4. **读取期间：** 全部采集及所需复验处于同一 FROZEN 窗口；监测准入和意外写入迹象，发生状态变化立即使本次结果无效。只读备份 token 不得拥有写权限。协调器/网络故障保持停写，不自动解冻。
5. **RESUMING：** 由操作者确认备份状态和当前 schema；明确批准恢复准入，更新 epoch 后重新开放。迁移若未获批准，本窗口只做备份，不把状态推进到 migration apply。失败也不自动启用生产恢复。

应用准入只能覆盖接入它的写者，不是数据库层全局锁。分批部署过程中旧版本仍可能写；必须先证明旧版本和旁路入口已退出、全部新版本都受控，再进入正式窗口。若无法证明，则不能声明 FROZEN，更不能依赖两次相同扫描消除风险。禁止以删除 FTS、修改真实业务数据或自动恢复整库来绕过停写问题。
