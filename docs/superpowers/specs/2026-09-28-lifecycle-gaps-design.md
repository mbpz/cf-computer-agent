# 生命周期缺口设计提案（C07）

日期：2026-09-28 UTC。来源：[C07 现状核对](../../product/2026-09-28-lifecycle-inventory.md)。

状态：**核对后的独立设计提案，尚未批准实施。** 不把本文件当成用户授权删除、生产迁移、自动清理或备份。C07 交付设计，不代表以下业务功能已实现。

## 目标与共同约束

保留当前管理员知识治理与 member-scoped 私有数据边界，复用现有 D1、DO/VFS、R2 和浏览器存储；不新建平行系统，不申请收费资源，不增加加密/备份前置条件。

- 私有操作仅用 session member_id；跨成员 ID/不存在均按已有 404 契约处理。管理员知识治理不静默扩成所有成员可清理。
- 删除、归档、隐藏、取消、清正文、擦除物理副本分别命名，UI 展示不可逆边界，不用统一“删除成功”混淆。
- 新增有界分页；清理操作有稳定 operationId/精确请求指纹和最小 tombstone。未知响应先 GET 对账，无确认不自动换键重做。
- 审计仅保存必要 actor/resource/action/version/time/result，不保留已请求删除的正文。操作 tombstone 不复制完整内容。
- 任何期限未获产品批准前，不启用新的 TTL 删除。现有知识 30 天和附件 24 小时宽限保持现状；不类推到任务、消息、通知。

## 方案取舍

1. 统一重写所有域生命周期：边界过大、会改变去重/FK/读取语义，拒绝作为本轮快速收尾方案。
2. 仅补 UI，不修跨存储协调：会把知识 purge 的已知竞态直接暴露，不能作为安全完成方案。
3. **建议按域最小增量**：先保护现有知识 purge，再复用现有管理员 API 补入口；任务、协作保留策略和环境 adapter 独立推进。每域独立测试与状态，不用 C07 勾选提升交付维度。

## LC-01 知识治理：保护已有能力，再接 UI（KB-012 / D03）

建议状态机：`active → trashed → purging → purged`；仅 `trashed → active` 允许恢复。继续使用现有 30 天截止规则，后续若需要 `trashed_at` 独立列，先明确历史回填，不默默改期限。

- 在删除外部内容之前，以资源/version/cutoff CAS 在 D1 记录唯一 purge intent 和不可恢复阶段。restore/rollback/publication 写路径必须在同一数据库条件中拒绝 purging，而不是先读后写。
- intent 保存固定 revision/path 集合、身份和最小执行进度；外部删除幂等，部分失败留 purging、明确告知不可恢复，不回退成可 restore。再次操作只续同一 intent。
- 外部删除确认后，同事务移除索引/派生数据并记录最小 tombstone。若 finalize 响应丢失，只读 receipt；不存在不能重新创建对象。不得声称 D1 与 VFS 有跨资源事务。
- 管理员回收站复用已有分页 GET；显示实际状态、截止时间、索引状态；恢复与不可逆 purge 分别确认。purging 只允许状态核对/同意图续作，不能显示普通恢复按钮。
- 必需新增验证：真实本地 VFS remover 与并发 restore 交错；claim 前/后冲突、删到一半失败、重启续作、外部已删而 finalize 响应丢失、两个管理员同对象竞争、撤权、审计失败与派生索引一致性。现有 D1-only race 用例不足。

## LC-02 私有任务：软删除与兼容边界（TSK-009 / C01）

建议保留硬删除历史（不能凭空恢复），新模型使用 `active/trashed/purging/purged` 与 deleted_at/version；暂不指定任务保留天数，必须批准后配置。

- 新 trash 动作与 task.deleted/trashed 审计、稳定收据同批条件写。trash 后任务所有读取面（列表、看板、目标/项目/日历/搜索/讨论授权）排除或显式呈现失效引用，不能仅过滤一个页面。
- 恢复只恢复原 member 的任务；关联对象已失效时显式报告，不夺取他人任务或用旧 ID 创建新对象。purge 保留最小重放标记，清理子项有固定范围和事务条件。
- 不静默把既有 DELETE 成功语义改为保留：先决定旧客户端兼容策略（旧契约维持或版本化），再改入口/API，避免旧客户端把已软删任务当成真正擦除。
- 验证：跨成员、子项/计数/讨论授权、并发编辑与 trash、restore 与 purge、相同操作重复、审计故障回滚、旧硬删对象不可恢复。

## LC-03 协作：数据保留不破坏重放（NTF-005 / MSG-005）

通知按 recipient，讨论按 context 当前权限。不能把整个共享线程当作某一参与者私有资产随意 purge。

- 消息优先设计“正文 redacted、结构/sequence/reply 锚点保留”与“整个线程关闭清理”两类动作；新删除权限需区分作者、上下文管理者、管理员，不能从可读推导可删。
- 消息 client key、通知 dedup key 从可清正文分离为最小去重标记；清正文后同键重放返回已删除/不可重放结果，不再次生成正文或通知。不得仅删除带唯一键的行来实现 TTL。
- 未读通知是否到期、作者可删窗口、共享消息期限及 tombstone 最短保存期都是待批准政策。政策未定不开自动任务，现有目标失效响应继续生效。
- 验证：撤权后删除/重放拒绝，shared 与 private context，删除回复父节点、并发发送序号、正文清理后旧键重放无复活、摘要计数与分页不泄漏、审计不带正文。

## LC-04 附件：显式补偿，不把解析 Cron 当清理（已有 orphan API）

保留 preview → 人工确认 keys → reclaim 的现有边界。建议未来把 cancel 的对象删除失败记录成有界 cleanup intent；对象引用声明与 reclaim 要通过版本/租约协议协调，不把 head + 查询引用 + delete 称作原子。

- 清理仅在已有存储可用时运行；当前不新增自动 Cron 或收费队列。若批准自动化，先定义处理上限、重试次数、失败可见性以及回收期间不得重新引用的协议。
- 验证：取消成功但 R2 delete 失败后显式续作，检查后新引用竞争、年轻对象跳过、重复 key、分页过界、已被另一清理者删除时幂等；任何阻断都不能扩大 key prefix。

## LC-05 环境与小模块：不扩大物理删除承诺（D04 / D03）

- 环境：将既有 deletion reconciler 接到正式 runtime 的账户隔离 adapter。adapter 在每次实际写前验证 origin/member/sessionEpoch，幂等删除运行时与 OPFS/IndexedDB 精确副本；失败保留可重跑状态。只依据显式 tombstone，不以空列表清库。
- 验证：真实存储前后检查、跨标签/退出换账户、异步写前切换身份、部分删除失败、离线重放；fixture callback 通过不能标记擦盘完成。云端备份恢复不在范围。
- 小模块：保持 Inbox archive、Calendar canceled、Focus completed 等现有状态名；若要永久删除，独立定义状态机和引用规则。收藏/保存视图维持已有硬删语义；最近访问 200 条裁剪不改成未获批准的天数策略。
- 私有笔记、投稿、会话、研究产物的成员数据删除/导出边界由 D03 核对后另起原子实现，不借清理之名删除未核对的数据。

## 实施入口与验收门槛

建议顺序 LC-01 → LC-02 → LC-03；LC-04/05 跟随各自现有模块计划。每一步先把新增行为和兼容范围提交用户确认，再 TDD 实施，不因“继续 checklist”将尚未批准的破坏性产品策略当成已授权。

每个实现切片必须保留：失败测试 → 最小实现 → 相关回归 → checklist/ledger 真实更新 → 本地 commit。发布与迁移仍属于 D08，原生真实身份/设备验证仍属于对应父项及 D05/D06。未批准期限、缺少正式 adapter、Mac 锁定分别是相应步骤的条件，不阻塞无关本地工作。
