# D02-R2 审核写入与恢复闭环设计

日期：2026-09-16。起点：`codex/admin-audit-recovery`，`2ca1349`。

状态：用户于 2026-09-16 确认书面设计，A/B/C 批已实现并本地验证。A 见[实施计划](../plans/2026-09-16-admin-review-replay-contract.md)与[验收证据](../../product/2026-09-16-admin-review-replay-contract-evidence.md)；B 见[实施计划](../plans/2026-09-16-admin-review-write-ui.md)与[本地证据](../../product/2026-09-16-admin-review-write-ui-evidence.md)；C 见[实施计划](../plans/2026-09-16-admin-review-notifications.md)与[本地证据](../../product/2026-09-16-admin-review-notifications-evidence.md)。D 待完成，不是 R2 整体完成或发布证据。D02-R1 的读取恢复成果保持不变。

## 目标与约束

- 同一提交、同一审核人、相同规范化决定可安全重试；不同决定或参数不能覆盖已经落地的审核。
- 发布成功与索引就绪分开表达，不能因搜索暂不可用而诱导用户重新创建发布。
- 提交者能收到一次对应的审核结果通知；通知与跳转不得扩大数据访问权限。
- 仅使用项目现有 Cloudflare 服务，不增加收费服务、外部队列或新依赖；本阶段不修改生产配置或执行远程迁移。
- 保留现有分页协议、权限检查、私有成员隔离和审计脱敏。审核人由认证主体确定，不能由请求指定。
- 本地实现、本地自动化、提交、部署、真实登录验收分别记录；任一子项通过不自动关闭 D02/R6-003/ADM-002。

## 已核对的现有实现

| 位置 | 现状 | 本设计的处理 |
| --- | --- | --- |
| `src/publication/repository.ts` 的 `createOrReadIntent` / `exactIntentOrThrow` | 按 submissionId 读取持久化发布意图，比较审核人、标题、目标、可见性、标签等参数 | 复用，不另建通用幂等键表 |
| `src/publication/repository.ts` 的 `decide` / `exactDecisionOrThrow` | 决定、状态和审计写入同一 batch；已有决定只允许相同审核人和决定、原因、说明重放 | 增补返回值一致性、并发和冲突证据 |
| `src/publication/service.ts` 的 `resumeIntent` / `recoverPending` | 发布内容与 D1 状态分步恢复；发布结果含 searchStatus，索引任务有恢复流程 | 保留恢复协议，避免把未完成索引误报成未发布 |
| `frontend/components/review/review-detail-data.ts` 的 `submitReviewDecision` | 返回 Promise<void>，丢弃服务端结果；驳回/退回说明固定为空 | 后续改为消费类型化结果与真实说明 |
| `src/notifications/types.ts`、`migrations/0036_workbench_notifications.sql` | 事件仅含任务/讨论类；目标不含 submission；已有收件人维度去重约束 | 后续扩展审核通知，不绕过存储约束和授权 |

发现的首批具体缺口：`decide` 首次构造的 `ReviewDecision.visibility` 原固定为 `admin_only`，但 INSERT 保存 `preview.requestedVisibility`，`findReview` 重放返回数据库值。对于请求共享可见性的提交，首次响应与重放响应因此存在差异。A 批已用真实 D1 复现并最小修复；详见本地证据。

## 方案选择

采用现有 publication intent / review 作为权威操作记录。submissionId 是当前一次审核生命周期的稳定标识；审核人和规范化载荷是重放匹配条件。前端保留本次发送的载荷快照，不为重试生成另一套身份。

不采用“新增通用 clientKey 幂等表”：已有不可逆决定及发布意图会与第二套状态形成双重权威，迁移和清理成本也超出本轮需要。不采用“只禁用按钮”：它不能解决跨标签页并发、响应丢失或服务重建。

本轮不新增退回后的重新提交生命周期。如果后续允许一个 submission 多次审核，应先引入显式轮次，再重新设计操作身份，不能沿用当前永久决定记录假装支持多轮。

## A. 首批：审核重放与冲突契约

范围：`src/publication/repository.ts`、`test/worker/m1-publication.test.ts`，必要时补 `test/unit/publication-service.test.ts`。不改变接口字段，不增加迁移。

1. `ReviewDecision` 首次响应与服务重建后的精确重放，在 submissionId、reviewerId、decision、reasonCode、note、title、visibility、createdAt 上完全一致。
2. 对驳回/退回，visibility 表示审核记录中的请求可见性，不表示已发布或授予读取权限；首次响应取值必须与持久化记录一致。
3. 同一决定的并发重试最终只保留一条 review 和对应的一条 audit，提交状态与决定一致。响应丢失后的重试返回权威结果。
4. 更换审核人、改变决定、原因或规范化后的说明，返回现有 `REVIEW_STATE_CONFLICT`；不覆盖原记录。非活动管理员仍被服务层拒绝，已有记录不成为鉴权旁路。
5. 发布保持现有 `PUBLICATION_STATE_CONFLICT`、`PUBLICATION_TARGET_INVALID` 边界；不绕过当前目标检查，也不承诺在目标失效后仍可恢复发布。继续覆盖进行中的发布与驳回互斥、发布并发只生成一份版本及审计。
6. 测试直接通过 PublicationService 和真实本地 D1 断言数据库副作用。只在模拟提交成功后响应丢失时代理底层返回，不替换真实事务。A 复核追加确定性读窗口测试：测试子类仅在实际预览读取前调度另一真实 service 完成决定，读写和事务仍由原实现执行。

本批验收：先观察共享可见性首次响应/重放不一致的失败，再做最小修复；覆盖两种决定及两种可见性；已有发布服务与 Worker 用例继续通过。该验收不等于整个 R2 完成。

## B. 第二批：前端权威结果与恢复交互

涉及 review-detail-data、审核队列/详情路由、详情组件和国际化资源。

- 发布结果必须携带并校验版本 ID、知识项 ID 与 searchStatus；驳回/退回必须校验 submissionId 与实际决定。异常成功载荷不能直接把页面改为成功。
- indexed 表达“已发布且可搜索”；pending/search_degraded/failed 分别说明索引未就绪或失败，但不得回退为待审核。现有恢复入口继续由有权限的管理员使用。
- 请求超时或网络错误不证明写入未发生。保留本次载荷，允许用户手动重试相同操作；不要静默自动重试，也不要在结果未知时切换成相反决定。
- 未知结果重试后收到 400/422（如目标失效），不能推断第一次未提交；继续锁定其他决定，只提供权威重读。首次明确校验拒绝才允许原表单修正。
- 驳回/退回说明通过现有 shadcn 风格表单录入；沿用服务端原因白名单和说明长度限制；错误保留输入，不把私密说明写入审计元数据。
- 401/403 清空受限数据；对象切换、离开页面、登出后迟到响应不得污染新页面。409 展示冲突并提供重读，不提供强制覆盖。
- 队列刷新保持原筛选和分页；完成项离开当前页后按现有分页边界处理，不清空用户查询。

## C. 第三批：审核结果通知

涉及 publication repository、notifications 类型/授权/前端映射、D1 迁移及迁移契约测试。该批单独编写实施计划，不能直接修改历史迁移。

- 为发布、驳回、退回修改定义对应审核事件，收件人从提交的持久化 submitterId 取得，不接受调用方指定。
- 通知以 submission 为关联目标，使被驳回或退回的内容也有合法落点。通知读取及点击必须检查当前提交归属或当前管理权限；不因通知存在而允许访问知识正文。
- 通知去重键使用 submissionId 与终态决定的稳定组合；新通知在决定最终落库的同一 D1 事务中创建，失败则事务回滚。发布 intent 保留供既有恢复机制重试。
- 内容写入或索引重试不能再创建通知。索引状态不改变审核结果通知的语义；发布通知只在发布最终落库后产生。
- 载荷只包含必要的事件信息和稳定标识，不复制正文或私密审核说明；目标失效或撤权时使用现有安全失效展示，不返回受限目标链接。
- 仅对新发生的决定产生通知，不批量追溯旧记录。上线前用带旧数据的迁移测试证明历史通知、已读状态和唯一约束保留，并同步 schema hash/count 与 release contracts。

## D. 第四批：故障矩阵与交付收口

- 同一载荷并发、不同载荷竞争、不同管理员竞争、服务重建后重放。
- 内容提交成功但返回丢失、D1 决定成功但返回丢失、最终事务失败、索引暂时失败后恢复。
- 一次决定对应一条审核记录、一次对应审计和一次提交者通知；失败不能留下不一致的半条业务记录。
- 管理员/普通成员/第二成员正向与越权检查；通知、列表、详情及目标跳转必须重新鉴权。
- 中英文、键盘、深浅主题和移动宽度的真实交互；本地自动化不替代真实登录与部署后验收。
- 同步 roadmap、产品审核 checklist、成熟度 checklist 和交付总账；不改写历史部署证据。
