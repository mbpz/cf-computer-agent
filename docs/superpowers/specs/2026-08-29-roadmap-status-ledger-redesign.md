# Roadmap 与交付状态总账重构设计

日期：2026-08-29

## 目标

把 README、Roadmap、AI 知识库原子 Checklist、前端 Checklist、历史实施计划和生产证据重新核对为一套不会混淆“代码完成”与“生产完成”的交付事实系统，并根据真实缺口重新安排后续功能顺序。

## 当前问题

现有文档分别在不同阶段形成，存在以下状态漂移：

- README 仍以旧 M1 状态描述产品，未完整体现工作台、任务、统一分页、独立滚动和菜单可用性。
- Roadmap 的里程碑结构以知识库演进为主，工作台功能被夹在 M2 中间，消息、通知、看板没有独立纵向交付顺序。
- AI Checklist 同时使用勾选框和 `L/W/P` 等证据缩写，不能直接回答“实现、验证、发布、验收分别完成到哪里”。
- 前端 Checklist 与 AI Checklist、Roadmap 存在部分重复，后续容易重复统计或遗漏。
- 历史 implementation plan 保留大量未同步勾选框，它们是执行档案，不应再作为当前完成度来源。
- 已实现、已通过本地门禁、已部署和已完成登录态浏览器验收经常被合并为一个“完成”结论。

## 权威状态模型

每个可交付原子统一使用四个独立状态维度：

| 维度 | 定义 | 最低证据 |
| --- | --- | --- |
| 实现 | 对应代码、schema、UI 或运维资产已经存在 | 文件路径、migration 或 commit |
| 验证 | 本地或 Workerd 确定性门禁通过 | 测试文件与可复跑命令 |
| 发布 | 所需 migration、Worker 或静态资产已进入目标环境 | 日期、version ID、migration 状态 |
| 验收 | 真实角色在目标环境完成用户旅程 | 角色、旅程、脱敏 request ID 或浏览器证据 |

状态值只允许：

- `done`：该维度有可复核证据。
- `partial`：只有部分范围或部分角色有证据。
- `pending`：尚未执行或没有证据。
- `n/a`：该原子客观上不需要该维度，必须写明原因。

禁止用 README 文字、截图、勾选框或口头确认替代上述证据。一个功能只有四个维度均为 `done` 或合理的 `n/a` 时，才能称为“完整完成”。

## 文档职责

### README

README 只负责：

- 产品定位与 Cloudflare 免费层边界。
- 当前能力地图。
- 当前发布成熟度摘要。
- 本地开发、验证和运维入口。
- 指向 Roadmap、状态总账和专题 Checklist。

README 不维护原子完成数，不复制完整 Roadmap，也不把本地门禁通过写成生产验收。

### ROADMAP

Roadmap 只负责纵向交付顺序：

- 每阶段必须形成可使用、可验证、可回滚的用户旅程。
- 每阶段列出目标、范围、前置依赖、退出标准和状态摘要。
- 原子任务只引用总账 ID，不在 Roadmap 中复制实现细节。

### 交付状态总账

新增 `docs/product/delivery-status-ledger.md`，作为当前完成情况的唯一权威汇总。每行字段固定为：

`ID｜功能｜优先级｜实现｜验证｜发布｜验收｜依赖｜证据｜备注`

总账按产品域组织：

- 身份与用户隔离
- AI 知识库与摄取
- 搜索、阅读与引用问答
- 工作台 Shell 与导航
- 任务
- 看板
- 通知
- 消息
- 管理员治理与统计
- 运维、恢复与免费层保护

### 专题 Checklist

- `ai-knowledge-base-checklist.md` 只保留知识、摄取、治理、搜索、Agent、身份和运维原子。
- `shadcn-ui-frontend-checklist.md` 只保留组件、页面交互、响应式、可访问性和前端发布原子。
- 两份 Checklist 的每个条目都引用总账 ID；勾选框表示“实现且验证完成”，发布与验收仍回到总账查看。
- 工作台的任务、看板、通知和消息原子在总账中单独成域，避免伪装成泛化前端任务。

### 历史规格与实施计划

`docs/superpowers/specs/` 与 `docs/superpowers/plans/` 是不可抹除的决策和执行档案。它们的复选框不再参与当前完成度统计，也不批量改写为完成。

## 重新分期

### R0 — 状态收口与生产证据

目标：确保当前已实现能力的本地、发布和真实角色证据边界准确。

重点缺口：

- 当前 main 的完整门禁与回滚点记录。
- 0033/0034 是否已远程应用。
- 当前 Worker 精确版本是否包含统一分页、任务、Shell 和菜单可用性。
- admin、contributor 的登录态浏览器旅程。
- 生产 signed automation 与拒绝路径复验。

### R1 — AI 知识库核心闭环

目标：文本和现有支持格式从提交、解析、审核、发布、搜索、阅读到严格引用问答形成稳定闭环。

重点缺口：

- 将已有本地/Workerd 能力补齐生产 migration 与真实文件证据。
- 完成免费文本模式和可选 R2 模式的清晰产品分层。
- 修复仍为 pending 的 P0/P1 摄取、治理、索引、搜索和引用原子。

### R2 — 工作台协作闭环

目标：让工作台不仅有菜单和页面壳，而具备个人执行与协作闭环。

纵向顺序：

1. 任务：补齐已有私人任务的详情、关联、筛选和验收。
2. 通知：站内通知收件箱、未读状态、跳转目标和幂等生成。
3. 看板：基于任务的视图与拖拽排序，不复制第二套任务数据。
4. 消息：先实现围绕任务/知识条目的上下文讨论，再评估独立私信。

所有用户数据必须按成员隔离；共享数据必须通过显式权限或对象关系开放。

### R3 — 治理、版本、回收与审计

目标：补齐批量审核、Revision diff/rollback、回收站、恢复、最终清理、审计和失败恢复。

### R4 — 成熟检索、阅读器与评测

目标：完成过滤、Saved View、混合检索降级、来源定位、相关知识、反向链接和量化评测。

### R5 — 来源工作台、研究产物与有界 Agent

目标：围绕选中来源进行多轮问答，生成可追溯产物，并让只读 Agent 在预算、审批和恢复边界内运行。

### R6 — 导出、恢复、容量保护与 1.0

目标：完成导出包、全新环境恢复演练、R2/D1 容量保护、运行手册和完整生产验收。

## 缺失功能判定规则

核对不能仅依据页面或路由是否存在。每个功能至少检查：

1. 前端入口与完整交互是否存在。
2. Worker 路由与输入输出合同是否存在。
3. D1/R2/DO 数据模型是否存在且按用户隔离。
4. 写操作是否有幂等、并发和失败恢复。
5. 列表是否使用统一数字分页。
6. 权限拒绝、404、空状态、错误状态是否有测试。
7. 是否有本地/Workerd 证据。
8. 是否有生产 migration/deploy 证据。
9. 是否有 admin/contributor 浏览器验收。

只存在菜单、Coming Soon 页面、静态卡片或测试 mock 的功能判定为“未实现”。

## 核对与更新流程

1. 读取 README、Roadmap、两份 Checklist、规格、实施计划和运维证据。
2. 从共享路由注册表、Worker routes、migration、前端页面和测试反向生成能力清单。
3. 为每个总账原子记录四级状态和证据。
4. 标记文档冲突、伪完成、重复项和无归属功能。
5. 更新 README、Roadmap 和两份专题 Checklist。
6. 新增缺失功能原子，优先处理用户隔离、幂等、分页和免费层边界。
7. 运行文档链接、ID 唯一性、状态枚举和 `git diff --check` 合同。

## 验收标准

- README、Roadmap、总账和 Checklist 不再对同一能力给出矛盾状态。
- 总账 ID 唯一，四个状态字段只使用允许值。
- 每个 Roadmap 退出标准都能映射到总账原子。
- 每个 ready 路由都有对应总账原子；每个 coming-soon 路由都有未实现任务。
- 消息、通知、看板和任务分别具有前端、服务端、数据隔离、幂等、分页和验收任务。
- 所有“已发布”与“已验收”结论都有日期和证据入口。
- 历史计划明确标注为执行档案，不参与完成度统计。
- 文档合同测试和 `git diff --check` 通过。
